# v0.2.0 모델 변경과 사용 안내

소프트웨어 v0.2.0은 HVAC 전력과 현열 공급을 같은 계산으로 연결한다. 기술 백서 문서 버전은 v1.1이다. 프로필의 기존 `profile_version=v0.1`은 고정 공간 입력의 생성 버전이며 소프트웨어·열 모델 버전과 다르다. 기준선 소스와 설정은 `baselines/v0.1.0`, 기존 실행은 `data/runs/full-30d`에 보존했다.

## 변경 이유와 범위

기존 모델은 HVAC 온도 효과와 전력을 독립적으로 정했다. 따라서 전력을 바꿔도 온도 궤적이 같을 수 있었다. v0.2는 전력에 상수 COP를 곱한 열량을 열수지에 넣고, 외피·환기·인원·조명·기타 발열·축열을 함께 적분한다. 열용량과 UA는 TOML로 분리했다. 수식·단위·계수의 의미는 `data_generation_models.md`를 따른다. 예약·이용 인원·공간 프로필·고장 난수 생성 방식은 유지했다. 제어는 달라진 온도에 반응하므로 HVAC 작동과 전력 소비는 달라질 수 있다.

## 실제 실행

현재 Windows 작업 폴더의 최상위 경로에서 다음과 같이 실행한다. 기존 ID는 덮어쓰지 않으므로 새 ID를 사용한다.

```powershell
.\시뮬레이터실행.ps1 simulate --days 30 --seed 20261102 --run-id my-v02-run
.\시뮬레이터실행.ps1 aggregate --run-id my-v02-run --minutes 5
.\시뮬레이터실행.ps1 validate --run-id my-v02-run
.\시뮬레이터실행.ps1 report --run-id my-v02-run
```

아래는 별도 macOS 환경에서 패키지를 설치한 경우의 명령이다. 현재 정리본에는 이 macOS 가상환경과 모듈 심볼릭 링크가 없다.

```bash
source .venv/bin/activate
python -m aiot_sim simulate --days 30 --seed 20261102 --run-id my-v02-run
python -m aiot_sim aggregate --run-id my-v02-run --minutes 5
python -m aiot_sim validate --run-id my-v02-run
python -m aiot_sim report --run-id my-v02-run
```

simulate는 원시 데이터 이후 별도 후처리로 레이블을 생성한다. `manifest.json`의 complete는 원시 생성 완료, `labeling.json`의 complete는 레이블 생성 완료다. 최종 판정은 `validation_report.json`의 valid와 physics_and_labels.valid를 확인한다. `label --run-id ...`는 **해당 실행 manifest에 저장된 규칙**으로 레이블을 다시 만든다. 기존 레이블 출력은 재작성하므로 새 규칙 실험은 새 실행 ID로 생성한다. label을 v0.1 실행에 적용하지 않는다.

## 파일과 시간 계약

기존 sensors, environment_truth, facility_states, energy_usage, reservations, occupancy_events와 주입 원인 anomaly_events의 컬럼 계약은 유지한다. 새 파일은 모두 평가용 truth이며 운영 입력으로 읽으면 미래 정보나 내부 정답이 누출될 수 있다.

- `truth/thermal_balance_1min/thermal_balance_YYYY-MM-DD.csv`: timestamp·room_id와 열수지 상세값. 행 t는 [t,t+1분)의 열교환이다. start_temperature는 truth(t), end_temperature는 다음 내부 상태다. 출력 간격이 5분이어도 열수지는 내부 1분마다 저장한다. C는 kJ/K, UA는 kW/K, 열률·전력은 kW, 구간 열량은 kWh다. 냉방 열량 음수·난방 양수, 외피/환기는 실내 유입 양수다. residual은 축열 변화−열유입 합이다. 외기, 구간 평균온도, 인원/기타/HVAC 열률, COP와 전력도 포함한다.
- `truth/fault_events.csv`: 원본 anomaly_events에 fault_category(sensor/equipment/occupancy) 추가. 원인 기간 [start,end)을 나타내며 실제 환경 임계 이탈과 같지 않다.
- `truth/environment_status_1min/environment_status_YYYY-MM-DD.csv`: fault_active와 세 원인 분류 플래그, 온도/습도/CO₂ 이탈 플래그, environment_anomaly_active(OR), recovery_active, recovery_variables를 기록한다. 기존 `_1min` 경로와 같이 상태 출력은 step_minutes 간격이다.
- `truth/environment_anomaly_events.csv`: 변수별 연속 범위 이탈 사건, 관측 min/max·설정 경계·closed/right_censored 상태. 마지막 관측 이후 회복을 알 수 없으면 right_censored다.
- `truth/recovery_events.csv`: cause_event_id, variable, fault_start/end, recovery_start/end, duration_minutes, status를 기록한다. 한 고장이 변수별 여러 회복 사건을 만들 수 있다.

## 레이블의 정확한 의미

환경 이상은 내부 truth에서 **온도 18–28°C, 상대습도 20–80%, CO₂ 350–1000 ppm의 포함 범위 바깥**이다. 경계값은 정상이다. 24시간 전체에 적용하며, 기존 분석의 점유 중 20–26°C 비율과는 다른 지표다. 범위는 설명을 위한 합성 가정이고 건강 위험·법적 기준·학교 운영 기준을 의미하지 않는다. 조도·소음은 아직 환경 이상 대상이 아니다.

설비/고밀도 원인이 끝난 직후 첫 관측에서 관련 변수가 범위 밖이면 회복 추적을 시작한다. HVAC 고장→온도, 환기 고장/고밀도→온도·습도·CO₂가 관련 변수다. 센서 고장만으로 물리 회복 사건을 만들지 않는다. 값이 범위 안에 처음 들어온 시각부터 5분 경과한 정상 관측까지 확인해야 recovered로 닫는다. 중간 이탈이면 안정 시간 측정을 다시 시작한다. 따라서 회복 구간에는 정상 범위에 진입한 뒤 안정 확인 시간도 포함한다.

새 관련 고장은 interrupted_by_fault, 실행 종료까지 정상 안정이 확인되지 않으면 right_censored다. 이 두 상태를 성공적인 회복으로 평균내면 안 된다. 5분 출력에서는 표본 사이 연속 정상 상태를 관측한 것이 아니라 정상 표본의 시간 간격을 확인한 것이다. 회복은 시간적 연관이고 고장의 인과적 기여를 분리한 결과가 아니다. 임계 이탈 없이 끝난 고장은 회복 사건을 만들지 않는다.

## 검증과 재현

`tools/v02/compare_runs.py`는 기준선과 새 30일 실행의 프로필·예약·입퇴실·주입 원인 CSV를 SHA-256으로 비교하고, 모든 truth 행의 timestamp·room_id·인원이 같은지 검사한다. 보존 스냅샷·기준선 데이터·원본 백서 해시도 검사한다. `comparison.json`과 `extreme_window.json`에 결과를 저장한다. `tools/v02/replay_baseline.py`는 보존 소스로 STU-B131의 14일을 재생한다. 같은 재생 ID는 다시 사용할 수 없다.

pytest는 전력 증가/냉난방 방향/COP/열용량/고장 중 공급 중단/분할 적분/열수지/회복 상태/재현성을 검사한다. validate는 전체 열수지와 COP·에너지 CSV 연계, truth 연속성, 설정 임계 상태와 회복 구간을 검증한다. 이는 수학·데이터 계약의 일관성을 검증하며 실측 정확도를 검증하지 않는다.

## 남은 한계와 다음 단계

상수 COP와 종합 열용량·UA는 가정이다. 일사·외벽 노드·장비 부분부하·습도 제어 잠열이 누락되며, 현열 수지가 닫혀도 건물 전체 에너지 정확성이 입증되지 않는다. `enable_energy_model=false`는 에너지 CSV를 0으로 내보내는 진단 옵션이고 실제 열 반응을 끄지 않는다. 에너지 비교 실행에서는 true를 사용한다. 모든 센서 고장 학습이 가능한 것이 아니라 현재 CO₂ 센서 네 유형만 구현되어 있다.

팀원은 새 실행을 데이터 버전으로 고정하고 시계열 학습/검증/시험 분할을 공유해야 한다. 실제 배포 성능은 별도 실측 검증이 필요하다. 우선 열용량·UA·COP·인체 발열의 민감도를 확인하고, 가능하면 익명 인원·온도·전력 관측으로 계수를 보정한다.

열수지 방법론은 EnergyPlus Engineering Reference의 zone air heat balance와 유효 열용량 개념을 참고했다. 본 프로젝트 계수의 출처라는 의미는 아니다.
https://energyplus.net/assets/nrel_custom/pdfs/pdfs_v22.1.0/EngineeringReference.pdf

COP는 같은 단위의 열 출력/전기 입력 비다.
https://www.energy.gov/cmei/femp/incorporate-minimum-efficiency-requirements-heating-and-cooling-products-federal

## 실제 30일 비교 결과

`v02-full-30d`는 63개 공간·2026-09-01–30·시드 20261102·1분 출력이다. 센서 2,721,600행과 5분 집계 544,320행, 내부 열수지 및 환경 상태 각각 2,721,600행이다. 전체 CSV 249개, 2,137,740,455 bytes다. pytest 46개가 통과했고 전체 데이터 검증 오류·경고는 0이다. 현열 수지 최대 절대 잔차는 약 3.59×10⁻¹⁵ kWh다.

기준선 온도 최소/평균/최대는 15.905/23.093/41.018°C, 새 실행은 20.101/23.783/27.715°C다. 점유 중 20–26°C 이탈은 181,474/754,282분(24.06%)에서 4,575/754,282분(0.61%)으로 바뀌었다. 총 전력량은 17,898.358→5,752.991 kWh다. **새 열 모델과 제어 반응에 따른 차이이며 실제 에너지 절감률·실측 정확도 향상으로 주장하지 않는다.**

입력 공간·프로필·예약·입퇴실·주입 원인 5개 파일의 해시가 동일하고 전체 truth의 시간·공간·인원 불일치는 0이다. 기준선 스냅샷 84개, 기존 데이터·보고서 190개와 백서 원본도 해시가 유지됐다. 같은 공간·하루의 새 버전 재실행에서 CSV 17개가 모두 동일했다. 전체 30일을 두 번 재생한 것은 아니다.

STU-B131의 41.018121°C 사례는 보존한 v0.1.0 소스로 해당 일 1,440행을 정확히 재현했다. 고장 시작 17:55에도 기존 온도는 이미 37.764°C였다. [17:55,18:29) 고장 중 증가량은 기존 약 3.254°C, 새 모델 약 0.678°C이며 같은 18:29의 새 온도는 26.417°C다. 이 고장 하나가 기존 고온 전체를 만들었다고 단정하지 않는다.

새 레이블에서 온도 18–28°C 이탈은 **0 공간·분**, 습도 이탈 102 공간·분, CO₂ 이탈 114,688 공간·분이며 합집합은 114,723 공간·분이다. 고장 원인 활성 42,821 공간·분과 다른 지표다. 따라서 이번 실행만으로 온도 환경 이상 양성 사례를 학습할 수 없다. 온도 고장 시나리오는 임계값을 사후에 좁혀 성능을 만들기보다 별도 조건·기간·설비 용량을 명시해 설계해야 한다.

회복 사건은 전부 CO₂에 관한 125건이다. recovered 124건의 지속시간은 안정 확인 포함 중앙값 21.5분, 최소 6분, 최대 373분이다. interrupted_by_fault 1건은 성공 회복 통계에서 제외했고 right_censored는 이번 실행에 없었다. 회복 활성은 6,211 공간·분이며 다른 원인 고장과 겹치는 16 공간·분을 포함한다.

원본 근거는 `deliverables/v0.2.0/comparison.json`, `label_summary.json`, `replay_verification.json`, `tests.log`와 실행 `reports/validation_report.json`이다. 임계값과 물리 계수는 여전히 합성 설계 가정이다.
